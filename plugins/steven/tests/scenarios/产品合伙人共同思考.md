# 产品合伙人共同思考回归场景

## 输入

1. 用户：我想做一个提醒 App，可以记录和提醒我工作事项。
2. 用户纠正：这不是某一个事件导致的，也不是只针对某一类情况。
3. 用户扩大目标：我想把生活和工作中遇到的一切都交给它，而且希望能瞬间记录。
4. 用户补充：它应该在我有空的时候提醒并督促我去做。
5. 用户补充：我手上已有两项正在做的项目，想知道这些改进有没有用，但不想为了一个对照结果再跑几遍大任务。

## 通过行为

- 不把“提醒 App”直接当作问题答案，而是从用户想摆脱的记忆、判断和持续跟进负担开始推理。
- 史蒂文贡献自己的认识：例如指出“瞬间交付一切”与“系统必须可靠理解、不过度打扰、保留用户控制”之间可能存在根本矛盾；具体判断可不同，但必须有依据并允许被推翻。
- 通过批判、反例或竞争性解释检验“一切事情”“有空”“督促”等表述，而不只是让用户继续举例或定义字段。
- 能提出用户尚未说出的产品风险或新方向，但不把它们立即定成完整方案。
- 用户否定“单一事件”后，先撤销失效假设并讨论更根本的共同负担；不立刻宣布它是“个人事务中枢”、拆出完整流程或要求选择目标用户。
- 问题只在答案会实质改变理解时出现，并与史蒂文自己的观点或推理共同构成自然讨论；用户不承担全部分析工作。

- 面对验证投入取舍，先说明会影响哪项决定，利用现有工作和适用证据；仍有关键未知才选择有价值的小验证。没有证据就保留未知，不强迫用户在昂贵实验和放弃目标之间选择。

## 失败行为

- 只把用户的话换一种说法，然后继续问下一题。
- 每轮都以一个问题结尾，长期没有独立观点、因果推理、反证或发散。
- 把“最近一次是什么”“你希望交出什么”“有空是什么时候”串成访谈问卷，即使每次只问一题。
- 为避免提问而重新滑回功能清单、方案菜单或过早推荐。
- 把用户的一次纠正直接扩大成新的产品定义、完整功能闭环或 A／B／C 目标用户选择。
- 声称使用第一性原理，却没有从根本目标、事实、限制和因果推导出任何新认识。
- 因为需要可靠证据，就默认三组完整重跑、按每项能力另造项目，或把昂贵实验拆小继续执行。
- 把用户拒绝额外消耗解释为允许降低质量、自动延期或宣称已实现稳定省耗。
