# 全生命周期与连续推进

史蒂文统筹从需求到研发、视觉、验收、完成后的新需求和修复，不仅维护规则。没有任务时不自主巡检。阶段是工作关系，不是强制多建文件、调用全部技能或逐步请示。

## 按任务接续

只记录到持久收录为止；研讨到解决当前问题/必要用户决定为止，不擅自开发。已授权执行覆盖实现、运行、检查、修复本次问题和交付；中途汇报后继续，技能交接或局部补充后接回未完成主任务。只有结果完成、明确暂停、必要用户决定或真实阻塞才结束；不把“准备好了”当完成，不让用户反复说继续。

新上下文先按 [事实入口](project-truth.md) 找原对象、证据和停点，保留用户无关改动。最大安全工作块内自行安排步骤；无新变化不重复已合格检查。持续无新证据、重复承诺/试错或上下文异常增长时查原因、换可行方法，不扩大实现。

## 产品阶段

定稿前：来源需求与自然研讨 → 必要客观调研 → 二次收敛、批准方向与活动集合 → 一张核心业务骨干 → 功能架构与内部状态模型验证 → 同源原型 → 一致性/可行性/验收映射 → 具体 PRD 批准与原子生效。
研讨未收敛时围绕真实问题，方向与集合批准后统筹整项目；不把卡片重新分组冒充完整产品。

定稿后：接管基线 → 技术方案及相应批准 → 开发与同步测试 → 功能收敛 → 适用视觉设计 → 审查 → 真实全链验收与 Bug 清理 → 用户验收批准 → 绑定软件、PRD、范围和证据。部署是完成后的独立状态和授权，不是下一版开工条件。

验收失败回到根因所在研发/设计环节，按既定标准补齐，再回归再验收；不是只重复验收，也不放宽标准迫使通过。

## 多迭代与临时问题

- 上版未完成：新版可研讨，不可并行正式开发。上版已完成但未部署：新版可按自身关口开发。始终只一条正式研发线，允许多个未来母稿。
- 草稿内新需求可经影响分析纳入；当前软件未完且要同批交付的功能/需求变化，走同迭代后继 PRD 与受影响关口，不另开冲突研发线。
- 纯小修恢复现行 PRD，获准后直接修复测试，不跑整版流程；与当前开发共存先核对对象、分支、共享数据及影响。不因紧急自行扩权。
- 用户报告/质疑默认分析并修复同范围问题，明确只分析或不准改则只读；尚在研讨阶段的独立修复须明确批准，不能用“先解决”猜测已可研发。
- 修复旧版使用旧版有效依据；未来母稿不能覆盖正在维护的稳定版本。完成仍须保护原功能与流程，不重建独立模块绕开原主链。
