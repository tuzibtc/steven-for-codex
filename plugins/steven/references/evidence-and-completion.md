# 证据与完成

“代码/配置已落地”“自动验证通过”“真实任务通过”“用户验收批准”是不同证据，不是五种需求业务状态。业务“已实现”必须来自项目 PRD 规定的正式验收批准；“已观察”不表示已改。完成与部署分开。

## 如何判断

每项要求关联适用 PRD、流程图及技术/设计标准 → 同一候选的入口/动作 → 预期与实际 → 原证据与结论。局部工作只审受影响项和依赖，整版验收覆盖全部批准范围及继承能力；从标准找遗漏，也从实际功能/流程反查越界和漏承接。

- 代码存在、导入成功、测试全绿不证明用户结果。保存要重开、关系要查原对象、发布要查对应回执；需要真实 UI 就连接实际服务操作并查看画面。独立补验的证据不能倒算为实现 Agent 已自验。
- 测试须有正确样例，也验证关键缺陷确实会被抓到；测试内复制实现或只匹配文字仅是低层证据。重要回归留在可重跑测试中，不只一次内联命令。
- 必需检查各自确认退出、正文、结果；失败、未知、跳过、阻塞不变绿，不用最后成功覆盖前项。保留必要证据，清理临时数据/资源；证据不可回读就明说。
- 技术缺陷回研发、视觉缺陷回设计，混合问题追到最早根因；修复及受影响回归后再验同一最终候选，不只反复验收或降低标准。已知范围内 Bug 未清零、断链/漏项/未验证未关闭时不报验收通过，不承诺绝无未知 Bug。
- 收尾从标准反查遗漏，再从实际轨迹反查每句完成声明；没有记录的 UI 操作、未运行测试、未同步停点不靠推测补齐。更新已有任务入口，只登记已发生证据，不提前标完成。有可行获准漏项就执行，不留给用户测出来。

## 能力产品的额外证据

规则存在只证明写了；结构检查只证明格式；新会话行为只证明受测场景；完整真实闭环才证明该范围可用。史蒂文等能力产品按其 PRD 增加隔离、陌生场景、原生比较、安装/加载及负例；不把这套额外实验强加普通业务项目。

新旧候选与题包/工具/权限分别锁定。候选新增或改变的行为须由其实际加载和结果证明；已验收能力只有内容、入口、依赖与适用条件未变，原证据可回读时才复用，不能复制旧报告通过标签。检查未通过或质量证据不足先修方法/实现，不把查漏责任交用户。

额外验证须能影响具体选择或避免有依据的重要损失；先判断现有证据、正常后续工作或局部复现能否回答。仍有必要才在批准的成本边界内补小验证，不默认完整三组重跑、逐项另造项目或为统计完整持续加样本，不把昂贵实验拆小绕过边界。必要质量回归保留；未知不判通过，也不自动降标或延期。

比较先固定同范围、同质量及可比条件，保留失败、重试、准备和复核成本。实际总 Token 按宿主定义处理输入、输出与缓存；费用、人工投入、等待及总历时分别记录，不可取得就保留未知。相对旧版改善、优于直接原生能力和用户减负分别判断，不互相抵扣；稳定收益须有适用场景的重复可比观察，不能择优、跨类型抵消或由一次小任务外推全版。验证自身的开销也计入投入。

有可行获准工作时，进度消息后继续执行，不把结果汇报当成结束本轮的理由。确需交回时说清结果、剩余目标、下一步由谁执行及是否需要用户；需要用户则给出推荐、原因、最少必要操作和可验证解除条件，不能只报“受阻／无权限”或让用户猜如何配合。操作入口先核实，无法核实就明确未知并继续可行查证，不编造按钮或把主要排查转交用户。用户完成操作后先回读原对象，满足条件便继续原授权任务，不再等“继续”；不满足则定位具体差异。内部验证通过且交付完整后才申请适用的正式验收；外部发布测试另获授权并放在内部测试后。
