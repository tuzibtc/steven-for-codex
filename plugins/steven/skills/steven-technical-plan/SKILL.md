# 技术方案

技术方案必须服务产品，不得把 M1–M9 等产品职责机械映射成目录、服务、命令或常驻 Agent。

## 设计顺序

1. 读取 PRD、产品/视觉设计、仓库规则、现有代码和运行环境。
2. 先比较删除、合并、复用和必要新增，选择质量与效率成立后的最佳总成本路线：模型推理负责判断；Skills 提供专业方法；小工具只做确定性事实读取、格式校验和重复操作；现成能力优先于自建平台。
3. 比较可行路线的产品贴合度、复杂度、维护成本、安全、许可证、迁移和回滚，给出一个推荐方案。
4. 写清组件职责、数据/状态权威源、关键接口、失败与恢复、依赖、测试和运行方式。
5. 把实施拆成能独立产生证据的工作包；先做高风险、可推翻假设的最小验证，再完成主路径。
6. 对替换式开发列出旧代码、测试、规则、配置、文档、资源、依赖和引用的删除清单；用户已有无关改动一律保留。

增量方案必须说明原版本功能、流程、入口、对象和数据的保持方式；分支接到原框架，不以重建模块替代协作。技术标准作为跨迭代可复用的现有文档/接口/测试契约维护，PRD 绑定适用版本；后继只更新受影响部分及理由，不逐版复制。经验进入现有标准与回归短索引，先查适用条件再复用。

方案必须逐条反查 PRD 要求和验收项，标出由 Codex/LLM 语义判断、专业 Skill、确定性脚本、外部原生能力分别承担什么。没有承接者的要求是缺口；同一产品事实被两个组件共同拥有是冲突。确定性脚本只能校验身份、格式、图关系、Git/平台读写和回读，不能判断需求含义、授权语义、产品方向或审美。

## 不做

- 不为了“像一个 OS”制造控制平面、后台服务、专用 UI 或第二套状态库。
- 不用长命令、固定词识别、海量脚本和闸门取代 Codex 的语义理解。
- 不因某个框架流行而整套引入；使用 [案例调研规则](../../references/source-benchmark.md)。

方案批准后交给 `steven-build` 持续实施。发现产品取舍变化才回到用户；普通实现判断由 Codex 负责。
