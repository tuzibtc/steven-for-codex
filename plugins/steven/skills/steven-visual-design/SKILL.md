# 视觉设计

目标是在获批产品上交付完整视觉结果，不改变前序已完成功能、流程、权限或数据。先读取现行 PRD、页面/功能基线与已有设计标准，按 [产品模型](../../references/product-model.md) 保持标准从属关系。

## 适用性与风格

完全可控设计适用界面，部分可控只改获准部分；无独立界面或宿主不可定制不造页面，也不额外要求跳过批准。若会减少原交付或改变基线才请用户决定。

已有获批风格/标准直接沿用。首次或明确获准重选风格时，先用同一代表性首页/主功能、相同内容与可比视口交付 **5—6 个风格迥异的轻量方向**：差异来自构图、字体、形态、层级和整体气质，不是换色。此时选的是风格，不是所有页面、组件和动效定稿；不提前做五六套完整网站。用户可拒绝全部，不强迫选。

## 标准 → 全面落实 → 交付

选定风格后，基于 PRD、已开发功能/页面和获批方向建立持久设计标准：原则、设计语言、参数/令牌、布局、字体、色彩、间距、组件/图标、状态、交互/动效、响应式、可访问性及适用例外；将 [设计审查](../steven-design-review/SKILL.md) 的适用平台底线一并纳入，不到交付才补。使用现有文档/组件来源，绑定版本和继承规则，后继 PRD 引用；不逐版重建、不复制第二套规范。

随后完成全部适用页面、组件、真实服务连接、加载/空/失败/禁用/成功与关键异常、窄屏/兼容/性能及交互细节。专业工具/外部 skill 按真实适配选择，先核许可与依赖，不把工具品牌风格当项目标准。新增样式/资源要确认页面实际加载，截图要实际看。

落地涉及代码时复用 [研发实施](../steven-build/SKILL.md) 的增量、回归与收尾方法，保留设计前行为作为对照；这是方法衔接，不重开研发阶段或增加批准。

最后先验证原业务主链与保持项，再审设计标准、实际画面和交互；两类都通过才交付。缺陷回对应研发/设计修复后再测。调用 steven-design-review，不把命令测试或美观截图代替功能回归。

用户说“不好看/不对”时先分析并给具体问题选项（局部组件、布局/细节、交互还是整体风格）和推荐；已选定特别是全面实施后，不默认推倒重选，只有明确说明或询问确认才改变风格。
