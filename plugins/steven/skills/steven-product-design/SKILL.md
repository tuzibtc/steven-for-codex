# 产品设计

产品设计解决“产品如何让用户完成目标”，不是把 PRD 机械拆成页面或代码模块。
先读取 [产品模型与表达](../../references/product-model.md)，内部模型未验证通过时不得投影或交付用户原型。

## 工作内容

1. 新建或整体调整产品设计时，以当前版本全部有效需求为输入；已有设计的局部调整只核对相关需求及必要依赖，先列出已知冲突、缺失依赖、非核心业务、权限、数据、异常、恢复和验收种子；不得把需求清单重新分类冒充完整产品。
   根据当前任务读取需要的产品事实和阶段规则，复用已读取且未变化的材料；任一读取输出明确错误时先补读，不能因同批最后一项成功就继续。
   当前项目已有完整 PRD、范围和验收条件时，就以它们为设计事实；不搜索无关项目的记忆、历史验收和旧样例来补充不存在的背景。只有某项必要事实在当前权威材料中真实缺失时，才按最小范围查找该事实；记忆不得反向改写当前 PRD。
2. 只形成一张项目级核心业务流程，钉住从真实触发到主要用户结果成立的价值骨干；支撑和内部控制由史蒂文补齐，不扩成用户审核图组。
3. 建立功能架构。每个职责明确产品价值、事实/状态所有权、提供与需要的接口、依赖、失败隔离、来源需求和验收；不按页面、文件夹或 Skill 数量机械分模块。
4. 为每个真实任务建立业务语义优先的内部状态模型，覆盖合法入口、事件、前置条件、迁移、结果、异常、恢复、版本和分支。用确定性项目测试检查可达性、非法跳转、关口绕过、终态、恢复重入、版本串线和孤立分支，再由 Codex 审核业务语义。
   状态模型和测试的体量必须与项目复杂度相称：优先使用转移表、表驱动用例和共用断言表达同等覆盖，不为显得完整而重复铺开大段样板、遍历或文字。压缩表达不得删除任何适用的正常、非法、异常、恢复、版本或分支语义。
5. 只有内部模型全绿后才投影用户产品原型。只保留用户需要看到、操作、理解或决定的部分；机器能判断的字段、锁定、对账、补偿和普通恢复不能变成用户节点。
6. 对有界面的产品制作可点击或真实低保真原型；对脚本、自动化或无独立页面的产品，不强行制造页面，只用真实宿主行为、输入输出和状态示例。
7. 对照 PRD、核心流程、功能架构、内部模型和用户原型，保证同一事件和合法路径无遗漏、无额外路径；两层任一失败不得请求用户审核。
   产品设计文档只保留用户、产品和下游实现真正需要的事实与证据摘要；已在可执行模型中完整表达的内部字段、去重键、迁移矩阵和重试细节不在文档中再抄一遍。
8. 用真实任务走通主路径和影响用户结果的关键失败/恢复，修复逻辑问题后再交给技术设计。用户只审核核心产品内容和必要体验，不审核内部状态完整性。

视觉表达不在这里拍脑袋决定；需要界面视觉时使用 `steven-visual-design`。技术限制只作为约束，不能未经讨论改变 PRD。若设计暴露产品事实缺口，回到 `steven-discovery`/`steven-prd`，而不是私改定稿。
