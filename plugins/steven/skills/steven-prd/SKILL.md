# PRD 治理

先读 [PRD 宪法](../../references/prd-constitution.md)。定稿或后继生效按 [受控操作](../../references/alignment-and-recovery.md)，阶段按 [生命周期](../../references/delivery-lifecycle.md)。研讨前完整读取相关来源卡，不用 PRD 转述替代原卡。

## 写成 Agent 可执行的产品合同

章节与详略按风险组织，不固定六章，也不无限追加规则。需要覆盖：来源与批准范围、用户问题与真实结果、目标/非目标、全局流程、功能关系、状态/权限/数据及异常恢复、增量变更与保持项、验收场景、适用专业标准和证据。把相互依赖的需求整合成完整产品，不只逐卡罗列。

从来源形成增量合同：现行保持项有生效依据，新增决定有用户批准，待定建议明确未批准；在条款旁或对应小节保留可回读来源。先核对这三者，再推导验收；没有出处的“原来/继续/仍然”须查证、改成建议或删除，不能靠行业惯例补全现状。无关未知不扩为必答问题。

关键规则写清触发、前置、行为、结果、失败/恢复和可核对标准，保留影响独立判断的理由与反例。简单低风险事实简写，关键链路细写；用户已经决定的范围可据合同细化，不重复询问其逻辑包含的情形。

技术与设计的持久标准在其原处维护，PRD 绑定有效身份/版本和适用范围；不抄成第二份。聊天过程、进度与运行日志不塞进 PRD，但决定依据不能丢。多对话研讨同一迭代母稿时按需求分工，写前核对最新基线，只合并已确认且不冲突的决定；不让陈旧会话覆盖新决定。

## 完整性与冻结

双向核对全部批准来源/有效末端承接与 PRD 要求，检查缺漏、多出、冲突和未决；再对照流程、技术/设计标准、实现基线和验收。旧版用户在用但漏记的能力按宪法查明处理，不能盲删或自动合法化。没有可实施/可验收标准的关键项不能定稿。

先完成内部自审修缮，再展示可读内容与关键差异。项目身份、底稿、可信私有远端/分支、精确文件与必要投影不可读时，仅可审核内容，明确不具备生效条件；不能用本地文件改名冒充定稿。完整语义批准后连续完成一次正式提交、推送与所有必要回读，不另索同一 Git 批准；任何必要项失败保持未生效。

定稿不可原地修改。新产品决定先获明确授权再建独立后继，核对影响并替换失效入口；普通实现修正不改 PRD。局部记录/修订完成后接回原未尽任务，在研讨就继续查证和处理下一问题，不把文档完成当整项完成或跨阶段授权。
