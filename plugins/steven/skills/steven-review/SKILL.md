# 产品与实现审查

先审产品结果，再审代码整洁度。不要只运行通用检查器。

## 审查顺序

1. 建立“PRD 要求 → 适用流程/技术/设计标准 → 实现证据 → 测试/真实结果”的对应关系，并从实际功能、对象和旧基线反查遗漏及越界。
2. 找缺失功能、越界功能、错误理解、被技术细节改变的产品行为和不可验收项。
3. 审查核心流程、异常/恢复、数据与权限、安全、性能、兼容性、依赖、可维护性和回滚。
4. 检查替换式开发是否残留旧代码、旧测试、旧规则、旧文档、无用依赖或冲突入口。
5. 区分确定缺陷、证据不足和建议优化；不把个人偏好伪装成 PRD 缺陷。

优先使用宿主原生代码审查与现有项目工具；外部审查仅在证据表明有缺口且授权适配时补充，不默认上传代码、添加模型服务或重复全量审查。用关键缺陷反例和正确样例核查测试判别力，检测不到缺陷不能把测试绿灯当充分证据。检查原链路、资源实际接入、回归留存与真实任务停点；源码存在不等于效果成立。

## 重新举证规则

- 正式产品审查从当前定稿 PRD 原文建立逐条矩阵；局部修改只覆盖受影响要求及必要依赖，不复制旧验收报告的结论。每条记录触发场景、应有判断、实现入口、实际行为、失败路径、证据层级和结论。
- “Skill 写了”“测试搜到了”“历史样例做过”分别只算规则、结构或历史证据；新增或改变的能力没有当前候选的新会话行为与真实结果，不得判通过。未变能力的旧证据按 [证据与完成](../../references/evidence-and-completion.md) 核对适用性后复用。配置维护只声明已验证的文件、安装和加载结果，不冒充行为改善，不强制重验全部产品能力。
- 同时审查阶段交接：研讨结论是否正确进入调研与 PRD，产品设计是否约束技术方案，实现是否受 PRD 控制，审查缺陷是否真实修复，验收失败是否回到最早根因。
- 对插件类产品，安装、路由和文件完整不能代替 PRD 要求的真实能力。陌生项目、重复观察及其它额外验证按现行 PRD、本次影响和已批准成本边界选择，未变能力沿上述规则复用适用证据；不自行增加通用验收门槛。
- 能直接修复且不改变产品事实的缺口交给 `steven-build`，修复后重新执行受影响行为场景；不得通过删减场景、放宽标准或把检查转给用户获得绿灯。
- 逐项读取各验证结果，确认没有前序失败被后续成功或最后一个退出状态掩盖；缺少独立成功证据的条目只能判为证据不足或未通过。

发现项按严重度、用户影响、证据、修复建议和对应 PRD 条目报告。修复后复核受影响范围。视觉和交互工艺交给 `steven-design-review`；最终产品结果由 `steven-acceptance` 判断。
