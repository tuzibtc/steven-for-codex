# 项目接管与入口判断

## 先确定事实

按 [项目事实](../../references/project-truth.md) 读取：当前目录、Git 仓库与分支、作用域规则、生效 PRD、`.steven` 状态和未提交改动。插件内 `scripts/inspect-project.mjs <项目目录> --summary` 可辅助读取 Git、PRD 指针、摘要和错位；保留全部异常和已跟踪改动，未跟踪路径仅报条目数，需要判断其内容时去掉 `--summary` 查看明细，不能据精简结果认定工作区干净。结果仍须与当前文件和外部权威源一起判断。只在需要时按授权读取相关 Codex 对话，不把对话记忆当唯一事实。

如果目标项目可能有多个，优先从路径、仓库、PRD 和用户最近指向中消歧；合理且可恢复的假设可直接采用并明确记录，只有选错会影响真实项目时才询问。

## 识别四种入口

入口和半途新需求版本门禁以 [研发全生命周期](../../references/delivery-lifecycle.md) 为准。

1. **仅记录**：把原始需求写入已绑定需求池并回读，不启动研发。
2. **研讨/打磨**：使用 `steven-discovery`，必要时 `steven-research`。
3. **开始/继续**：找到当前阶段和未完成结果，路由到对应 Skill，不从头重做。
4. **迭代已完成版本**：先保留现行版本，明确变更相对基线，再进入研讨和后继 PRD。

## 接管结果

内部形成一个简短基线：项目、PRD、当前阶段、用户目标、已有证据、未完成事项、保护边界。用户只需看到大白话结论和真正需要决定的内容。

接管核对全部关联来源卡，局部需求研讨完整读相关卡正文、评论和影响判断的附件；记录已读覆盖及变化，避免后续逐轮全读。处理需求截图时按 [需求池的附件规则](../../references/demand-pool-and-state.md#需求附件) 筛选、保存及回读。Obsidian 只打开和索引同一项目文件，不复制第二份文档或建立自动双向同步，也不每次继续都重开应用。

不要因状态文件缺失就创建复杂台账；但开始一个需要持续研发的新项目时，如果项目身份、可信私有仓库和需求池已经绑定，应先初始化可验证的最小状态底稿，现行/在编 PRD 都允许明确为空。不得为了让状态校验通过而创建空白 PRD，也不得等到技术方案阶段才补建定稿所必需的项目身份。不得触碰用户明确排除的真实项目。

仅记录、正式提取、P/D、多项目承接和写后回读必须执行 [需求池、项目承接与状态操作](../../references/demand-pool-and-state.md)。一次混合表达要先拆出新需求、产品变化、Bug 和纯执行单元，让每个单元走自己的路径，最后合并一次人话回执；任何轻路径都不能替其它单元绕过 PRD 或授权。

“继续”不能只凭聊天印象：找到最早尚未取得合格证据的关口继续。旧报告声称通过但只有规则文字、静态检查或无法回读的历史样例时，应降为待证，不从更晚阶段硬接。

仅记录只有在需求池权威端写入回读、授权状态底稿同步校验以及该底稿的可信 Git 远端回读全部一致后才算完成。任一步失败都按同一 Issue 幂等恢复，不重复建卡。若测试限制、绑定、权限或外部故障使写入没有发生，直说“尚未持久保存”；若只完成一部分，直说“已经部分写入但仍在对齐阻塞”，保留不推进边界并给出以后怎样完成，不能把对话里的临时复述或 GitHub 单边成功称为已经完整收录。
